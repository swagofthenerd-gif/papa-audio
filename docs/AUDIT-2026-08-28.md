# Papa Audio — bug audit and fix plan

Audit run 2026-08-28, against `feature/library-management-and-qa-fixes` at `b456a57`
(635 tests passing). **No source was changed by this audit** — it is a findings
document only.

## How to read this

57 bugs, every one reproduced by executing the code or by a mechanical
cross-check whose method is stated. Where verification showed I was wrong, the
candidate was discarded rather than listed — five were, and they are named in
"Checked and clean" at the bottom so nobody re-investigates them.

This is a companion to `docs/STABILITY-250.md`, not a replacement. That document
covers 250 catalogued items (125 now DONE). **None of the 57 below is a duplicate
of an OPEN item there** — they are new.

Each entry gives: what is wrong, how it was confirmed, and what the fix has to
do. Fix order is by tier, and Tier 0 exists because five of these are regressions
introduced by the previous session's work.

| Tier | What | Count |
|---|---|---|
| 0 | Regressions from the last session — fix first | 5 |
| 1 | Silent data loss and playback failure | 9 |
| 2 | Features that are dead or lie about what they did | 14 |
| 3 | Long-session stability: growth, leaks, blocking | 12 |
| 4 | Interaction and input: click, key, swipe, hold | 9 |
| 5 | Correctness of numbers, dates and formatting | 8 |

## Tier 0 — regressions from the previous session

These were introduced by the 125-item fix round. They are first because they
broke things that worked, and because two of them defeat guards added in the same
round.

### 0.1 [FIXED] The tray tooltip is wiped a fraction of a second after it is set

`update-now-playing` sets a correct tooltip ("Papa Audio — Snow Goose — Camel",
main.js:3329). The item-201 change added `refreshTrayTooltip()` on every `paused`,
`engineDown`, `engineRecovered` and `engineFailed` event, and it reads
`_trayTrack`, which is fed **only** by `ipcMain.on('update-tray-tooltip')`.
Nothing can send that channel: preload lists `'update-tray-tooltip'` in the
`on()` **receive** allowlist and exposes no send method. So `_trayTrack` is
permanently null and every play/pause overwrites the good tooltip with a bare
"Papa Audio".

**Fix.** Either feed `_trayTrack` from the `update-now-playing` payload (it
already carries title and artist), or delete `refreshTrayTooltip`'s name handling
and let `update-now-playing` own the tooltip, calling it only to append the
engine state. Do not add a send path for `update-tray-tooltip` — it is redundant
with `update-now-playing`.

### 0.2 [FIXED] The 60-second IPC deadline breaks every operation that waits on a human

Five handlers open a dialog or a window and are absent from
`IPC_TIMEOUT_OVERRIDES`, so they inherit `IPC_DEFAULT_TIMEOUT_MS = 60000`:
`add-music-folder`, `library-pick-artwork`, `slsk-set-download-dir`,
`save-lyrics`, `yt-auth-start`. Confirmed by matching every handler whose body
calls `showOpenDialog` / `new BrowserWindow` / polls-until-the-user-acts against
the exemption table.

`yt-auth-start` is the worst: a Google sign-in with 2FA routinely takes longer
than a minute, and the handler polls for the cookie until the window closes, so
the invoke rejects while the window is still open.

`add-music-folder` is the most damaging: it commits the folder to the store and
restarts the watcher **before** returning (main.js:5060-5069). Spend over a
minute in the file dialog and the change lands in main while the renderer sees a
rejected promise — the folder is added but never shown, and re-adding is a no-op
because `folders.includes` is already true.

**Fix.** Add all five to the exemption table with `0`. Better: exempt by
category — any handler that awaits user input must never be deadlined — and add a
test asserting that every handler containing `showOpenDialog`, `showSaveDialog`,
`showMessageBox` or `new BrowserWindow` has a `0` entry.

### 0.3 [FIXED] Two Soulseek searches are cancelled by the next search

`slsk-search` takes a `generation`, and `cancelSearchesExcept` kills every live
search whose generation differs. The two searches issued from the assistant panel
(renderer.js:7651 and 8020) do not pass one, so they register as generation 0 and
are cancelled by the next ordinary search. They use 45 s and 60 s timeouts, so the
window is wide, and the result comes back `{results: [], cancelled: true}` which
the caller reads as "found nothing". Confirmed by an IPC argument-shape sweep.

**Fix.** Pass a generation from those two call sites. They are not the main search
so they need their own generation space — give background searches a negative or
namespaced generation that `cancelSearchesExcept` never touches, rather than
overloading the UI search counter.

### 0.4 [FIXED] A search whose poll throws leaks, and `_cancelledSearches` grows forever

`_liveSearches.delete(id)` sits after the polling loop rather than in a `finally`,
so any throw from `slskdFetch` inside the loop — a 429, a 500, a socket error —
skips it. `_liveSearches` self-heals on the next search, but `_cancelledSearches`
is only cleaned inside the handler's cancelled branch, which a thrown search never
reaches, so that Set grows monotonically.

**Fix.** `try { ... } finally { _liveSearches.delete(id); _cancelledSearches.delete(id) }`.

### 0.5 [FIXED] Every Soulseek Retry / Saved-libraries / Show-more button is unstyled

`.slsk-retry-btn` is used on four `<button>`s with no other class
(renderer.js:8696, 8713, 8755, 8756) plus the Show-more button added last session,
and has no CSS rule — so they render with browser-default chrome inside a dark
theme.

**Fix.** Add a rule, or reuse `.secondary`/`.mg-btn`.

## Tier 1 — silent data loss and playback failure

### 1.1 [FIXED] A percent-escape in a filename gets the track deleted from the queue

The renderer sets `audio.src = 'file://' + rawPath` with no encoding, and the
shim's `_pathOf` runs `decodeURI` on the result. Confirmed by execution:
`/m/Track%20One.flac` becomes `/m/Track One.flac` and `/m/50%25 Off.flac` becomes
`/m/50% Off.flac` — 2 of 7 realistic paths do not survive the round trip. mpv is
then asked for a path that does not exist, and because `track-exists` is asked
about that same decoded path it answers "confirmed missing", so
`dropMissingTrack` splices a **present** file out of the queue. The decode is
guarding against an encoding that never happened.

**Fix.** Stop round-tripping paths through a URL at all — pass the raw path over
IPC and keep `src` as an opaque token, or `encodeURI` on the way in so the decode
is symmetrical. Add a test with `%20`, `%25`, `#` and a literal `+` in the name.

### 1.2 [FIXED] Whitespace in a tag splits one album into several

`albumKeyOf` (src/tag-edit.js) lowercases but never trims. Confirmed by
execution: `Camel`/`Camel `/` The Snow Goose` produce three different keys and
three different md5 album ids. `buildAlbums` (main.js:3251) groups by that key and
the artwork filename is that hash (main.js:2223), so one album with inconsistent
tag padding appears as several albums, each with its own cover, rating and notes.
Untrimmed tags are routine in Soulseek rips.

**Fix.** `.trim()` in `albumKeyOf`, plus collapse internal whitespace. This
changes album ids, so it needs a migration: build the old and new key for every
track, and rename artwork files and remap the `albumIdAliases`, ratings and notes
keys. Do not ship the trim without the migration or every album loses its art.

### 1.3 [FIXED] A cancelled download can never be re-requested, ever

`addItem` returns `null` when `done[key]` is set, `recordAbandoned` sets
`done[key]='abandoned'`, and the abandoned set is persisted and restored on every
launch (main.js:4269, 4294). Confirmed by execution: after a cancel, `addItem` for
the same path returns null and nothing is queued — with no feedback, because the
caller ignores the return value. A mis-click is unrecoverable short of editing
`download-scheduler.json` by hand.

**Fix.** Distinguish "the scheduler must not re-request this" from "the user has
asked again". An explicit enqueue should clear `done[key]`. Have `addItem` return
a reason rather than `null` so the caller can say "already cancelled — re-add?".

### 1.4 [FIXED] A file that exhausted its attempts cannot be retried with a better source

Same mechanism with `done[key]='exhausted'`. Confirmed by execution: `addItem`
refuses it, and `starvedItems` skips it, so the alternate-source search that
exists for exactly this case never runs on it.

**Fix.** As 1.3, plus let `addSources` on an exhausted key reset `attempts` and
return it to pending — a genuinely new source is new information.

### 1.5 [FIXED] Two albums sharing a track filename block each other's downloads

`fileIdentity` is the bare lowercased basename, and `planDispatch` refuses to
dispatch anything whose basename matches an in-flight transfer
(`inflightIdentities`). Confirmed by execution: with `/AlbumA/01 - Intro.flac` in
flight from peerA, `/AlbumB/01 - Intro.flac` from peerB is never dispatched —
`planDispatch` returns `[]` — even though they are different files from different
peers. `01 - Intro.flac`, `01.flac` and `Track01.flac` are as common as filenames
get.

**Fix.** Identity must include the remote folder, as `dlAbandonByFilename` now
does: `dlRemoteDir(path) + '/' + basename`. Keep the basename-only check as a
same-folder tiebreak, not a global one.

### 1.6 [FIXED] A download that stalls at the attempt limit becomes a permanent zombie

`recordStall` pushes the entry back into `pending` without checking `attempts`.
Confirmed by execution: at `attempts === maxAttempts` the entry sits in `pending`
where `planDispatch` skips it, `starvedItems` skips it (so no fresh-source search
runs), it is never written to `done`, and `stats()` keeps reporting it as pending.
It is persisted, so it survives restarts and shows as a download waiting forever.

**Fix.** In `recordStall`, if `attempts >= maxAttempts`, write
`done[key]='exhausted'` instead of re-queueing. Add an invariant test: no entry in
`pending` may have `attempts >= maxAttempts`.

### 1.7 [FIXED] A failed artwork download is cached as a permanently broken JPEG

`httpsGet` (main.js:3999) follows redirects but never checks `res.statusCode` — a
404, 403 or 500 body is resolved as if it were the payload. `fetch-album-art` then
does `fs.writeFileSync(cached, imgBuf)` with no content-type or magic-byte check
(main.js:4029). Because the next call short-circuits on `fs.existsSync(cached)`,
that album's artwork can never be fetched again: the grid shows the `onerror`
fallback forever and "Find artwork" skips it because the handler reports success.
One transient network failure poisons that album permanently.

**Fix.** Reject non-2xx in `httpsGet`. Check the first bytes are `FFD8FF` (JPEG)
or `89504E47` (PNG) before writing. Write to a temp file and rename. Never treat
`existsSync` as "we already have art" — check the file is non-trivially sized and
decodable, or keep a sidecar marker for "fetch failed, retry after N days".

### 1.8 [FIXED] Album art falls back to the first search result with no name match

`fetch-album-art` tries artist+album, then album-only, then `data.results[0]`
(main.js:4023). With `limit=8` on a search of `"artist album"`, the first result
for anything obscure is routinely a different release. Combined with 1.7 the wrong
cover is then cached permanently.

**Fix.** Drop the `results[0]` fallback. No match means no art.

### 1.9 [FIXED] The startup restore overwrites whatever the user started playing

`init()` arms `setTimeout(restorePlaybackState, 1200)` (renderer.js:675).
`restorePlaybackState` awaits `getPlaybackState()` and then unconditionally sets
`state.queue`, `state.queueIndex` and `audio.src` — **no staleness guard of any
kind**: it does not check `state.isPlaying`, whether a queue already exists, or a
generation. Click an album within the first ~1.2 s of launch (or during the await)
and the previous session's track replaces it. It then awaits `getSavedQueues()`
and replaces `state.queue` a second time with the `_auto` queue.

**Fix.** Take a generation at entry and bail after each await if the user has
touched the queue since; or simply `if (state.queue.length) return` at the top and
after each await.

## Tier 2 — features that are dead, or that lie about what they did

Each of these is code that exists, looks finished, and cannot do its job. They
are grouped because the fix is the same shape: either wire it or delete it, and
say which in the commit.

### 2.1 [FIXED] The whole embedded-browser feature is unreachable

main creates a `BrowserView`, maintains `updateBrowserBounds`, reserves
`LAYOUT.BROWSER_NAV`, and registers eleven control channels — `browser-back`,
`browser-forward`, `browser-navigate`, `browser-refresh`, `browser-stop`,
`browser-zoom-in`, `browser-zoom-out`, `browser-zoom-reset`, `show-browser`,
`hide-browser`, `open-browser-devtools`. Confirmed by diffing every `ipcMain.on`
against every `ipcRenderer.send` in preload: **none** of the eleven is exposed, so
nothing can drive it. The five `browser-*` push channels main sends are therefore
also pointless.

**Fix.** Decide. If the in-app browser is wanted, expose the eleven and build the
nav bar. If not, delete the BrowserView, the layout reservation, the eleven
handlers and the five pushes — that is several hundred lines and one fewer
`webContents` to reason about during a close race.

### 2.2 [FIXED] The sites feature cannot be used at all

`#add-site-dialog` (index.html:543-554) has a URL field, a name field and
Cancel/Add buttons, and **no renderer script references any of them** — nothing
shows the dialog, nothing handles the buttons. main registers `save-site` and
`remove-site`; preload exposes neither. `.site-item-del` in the renderer is the
music-**folder** remove button wearing a "site" class name.

**Fix.** Delete the dialog and both handlers, or wire them. If wiring: rename
`.site-item-del` so the folder list and the site list are not sharing a class.

### 2.3 [FIXED] "Configure Shortcuts" cannot configure anything

`renderShortcutsConfig` (renderer.js:13414) builds its rows from
`DEFAULT_SHORTCUTS` — not from the user's `_shortcuts` — and each row is
`<kbd>key</kbd><span>action</span>`: no input, no click handler, no key capture.
The only working control is "Reset to Defaults", which resets a value nothing
reads. Confirmed by tracing the global keydown handler, which tests literal keys
(`e.key === 'k'`, `e.key === 'z'`, …) and never consults `_shortcuts` or
`getShortcut` — `getShortcut` is referenced nowhere in the codebase.

**Fix.** Route every keydown test through `getShortcut(action)` and add a capture
row per action, or remove the dialog and the `papa-shortcuts` key so the app does
not advertise a setting it ignores.

### 2.4 [FIXED] Electron downloads cannot be cancelled

`ipcMain.on('cancel-download')` has no preload send path. The
`dl-started`/`dl-progress`/`dl-complete` events for those downloads are also
unlistened (already recorded as item 256 in STABILITY-250).

### 2.5 [FIXED] `show-notification` and the general-settings pair are unreachable

`ipcMain.on('show-notification')`, `ipcMain.on('save-general-settings')` and
`ipcMain.handle('get-general-settings')` have no preload exposure. Of main's 132
`handle` and 46 `on` registrations, **18 cannot be called by anything**.

**Fix.** One test, next to `test/preload-surface.test.js`, asserting the reverse
direction: every `ipcMain` registration is either reachable from preload or listed
in a documented exceptions map with a reason. That is what would have caught all
of 2.1–2.5 at once.

### 2.6 [FIXED] Torrents ignore the configured download folder

`_torrentAdd` (main.js:314) reads
`store.get('downloadDir', '/mnt/data/MUSIC/Downloads')`. Nothing ever writes a
top-level `downloadDir` — the folder picker writes `slskConfig.downloadDir`
(main.js:4926). Confirmed by a store-key symmetry sweep. Every torrent goes to
that literal path regardless of the setting, and on a machine without `/mnt/data`
it goes somewhere the user never chose. `slskdApiCreds` is read but never written
either, so the API credentials cannot be configured despite the code reading as
though they can.

**Fix.** Read `_downloadDir()`. Delete the hardcoded absolute path — a default
should be derived, never a literal from one machine.

### 2.7 [FIXED] The Wikipedia artist photo is fetched and thrown away

`loadArtistBio` (renderer.js:4045, 4051) writes the fetched thumbnail into
`#artist-portrait-img` and `#artist-hero-bg-img`. Neither element is ever created
— the artist hero renders `.artist-hero-art` with an id-less `<img>`. Confirmed by
checking all 311 referenced ids against every id in index.html plus every id the
JS creates: only these two and one dynamically-created banner are absent. So the
network request runs on every artist page and the result is discarded; the hero
always shows the first album's cover.

**Fix.** Give the hero `<img>` an id and use it, or drop the thumbnail handling.
Note `.artist-bio-photo` and `.artist-hero-bio` are in item 250's dead-CSS list —
this feature was half-removed once already.

### 2.8 [FIXED] Two achievement badges can never be awarded

"Skip Happy" and "Completionist+" (renderer.js:4990-4991) are `_needsPosition:
true`, and the gate at 5000 hides any such badge unless some history entry has a
`position`. `addPlayHistory` (renderer.js:3915) sends filePath, title, artist,
album, artPath, duration and ts — never position. So `_hasPosition` is always
false. They also divide by `p.duration` while guarding on `_histDur(p)` (the
library fallback), so even with position recorded they would misclassify every
entry written before the duration field existed.

**Fix.** Either record position in `addPlayHistory` (it is available as
`audio.currentTime` at the 30 s mark) and fix the divisor to use `_histDur(p)`, or
delete both badges.

### 2.9 [FIXED] The stats page advertises a range it does not have

`state.statsRange` (renderer.js:29) is initialised to `'month'` and no control
anywhere sets it — three of its four values are unreachable. The header renders
"This Month" from it while every figure on the page is computed from a hardcoded
rolling 30 days.

### 2.10 [FIXED] Compact sidebar mode is saved and never restored

renderer.js:12146 writes `papa_compact_sidebar` on every right-click toggle and
nothing reads it, so it resets on every launch. Confirmed by a write/read symmetry
sweep of every localStorage key. The resized sidebar width (`--sidebar-w`) is not
persisted at all, and the two mechanisms fight: the toggle sets
`sidebar.style.width` while the resizer sets a CSS custom property.

### 2.11 [FIXED] Swiping a Discover card accomplishes nothing

The mouseup handler adds `swipe-left`/`swipe-right`, removes the node after 300 ms,
and returns — no dismissal recorded, nothing liked or hidden, no state written.
The card reappears on the next Home render. The gesture is animation only.

### 2.12 [FIXED] Three YouTube download buttons are permanently stuck after one click

renderer.js:3406, 3542, 3770 do `btn.disabled = true; btn.innerHTML = '…'` then
`await window.api.ytDownload(...)` and never touch the button again — no success
state, no failure state, no re-enable. The button reads "…" forever whether the
download worked or not, and cannot be retried.

### 2.13 [FIXED] The Soulseek credentials dialog locks itself out on any failure

renderer.js:11249 sets `saveBtn.disabled = true` and the label to `Connecting…`,
then `await window.api.slskConfigure(...)` with no try/catch. A rejection leaves
the dialog open with a dead button, no error, and no way to retry but closing and
reopening. The same shape at renderer.js:11074 and 11094 ("Queuing N…" on the peer
browser's folder/tree download buttons) and at 4384 ("New folder" disables the
folder select and nothing re-enables it, so there is no way back to picking an
existing folder).

**Fix.** Every async click handler that disables its button needs `try/finally`.
Worth a lint rule or a test: `\.disabled = true` inside an async function must have
a `finally` in the same function.

### 2.14 [FIXED] `alreadyDone` on `slsk-cancel-transfer` is never sent

None of the eight call sites passes it, so the expensive branch it exists to skip
always runs. Its own comment says the lookup "costs a FULL /transfers/downloads
fetch (~1 MB here)" and that clearing a large completed list "used to pay that
once per item" — which is still exactly what happens.

## Tier 3 — long-session stability

This is the tier that matters for "rock solid over a long session". Every item
here is something that grows, leaks or blocks the longer the app runs.

### 3.1 [FIXED] Sixteen native `alert`/`confirm`/`prompt` calls block the whole renderer

renderer.js:5521 carries the comment *"Was a native confirm(), which blocks the
renderer and mpv's IPC callbacks in a frameless app that uses its own dialogs
everywhere else"* — one instance was replaced and sixteen were left. Confirmed by
checking each of the twenty occurrences for a local shadow (three are local
`confirm` functions and are fine):

`saveLibPreset` prompt+confirm (1654, 1672), `renderLibrary` confirm (2060),
`editField` prompt (2100), `renderAlbum` note prompt (2266), `renderPlaylist`
delete confirm (4583), `initChatSidebar` confirm (8430),
`_verifySurroundWhenDone` two alerts (8584, 8589), `_renderTorrentSection`
confirm (9476), `renderDownloads` two confirms (10484, 10567),
`bindSlskSearchEvents` alert (10606), `showSlskConfigModal` alert (11247),
volume prompt (12077), clear-queue confirm (12972).

While one is open the renderer's event loop is stopped: the progress bar freezes,
the 1 s reconcile tick stops, the 1 Hz extension sync stops, the downloads poll
stops, and player events queue up. Walk away with one open and the UI is frozen
until it is answered.

**Fix.** Replace each with the app's own modal (`_mgConfirm` already exists) or a
snackbar with an Undo where the action is reversible — which is what 5521 did.
Then add a test forbidding global `alert`/`confirm`/`prompt` in renderer scripts.

### 3.2 [FIXED] A synchronous file write runs once a second, all through playback

`writeNowPlaying` (main.js:824) is `fs.writeFileSync`. It is called from
`update-now-playing`, which the renderer sends from `syncExtension()` — and
`setInterval(() => { if (state.isPlaying) syncExtension() }, 1000)`
(renderer.js:13486) fires it every second for the whole time anything is playing.
Tier 3 of the previous round moved the side stores and the logger off the sync
path and left this one behind.

**Fix.** `fs.promises.writeFile` with the same coalescing the side stores use, or
route it through a `SideStore`.

### 3.3 [FIXED] The slskd search cache's cap of 200 is never enforced

`_searchCacheSet` (main.js:4090) evicts only entries older than the 5-minute TTL,
so a run of distinct searches inside that window grows the Map without limit.
Confirmed by simulation: 1000 distinct searches leave 1000 entries. Each entry
holds a whole search response, and the search is issued with `responseLimit:
5000`, so this is potentially megabytes per entry for the life of the process.

### 3.4 [FIXED] The YouTube URL cache has the same defect

`resolveYtUrl` (main.js:177) evicts only expired entries when size exceeds 200.
Confirmed by simulation: 1000 unexpired resolutions leave 1000 entries.
Pre-resolution runs five at a time from search results, so it fills quickly.

**Fix for 3.3 and 3.4.** After the TTL sweep, if still over the cap, drop oldest-
first until under it. The renderer already has `_cacheGet`/`_cacheSet` doing
exactly this (item 78) — lift that into a shared module and use it in main.

### 3.5 [FIXED] `_ytDownloads` in main never removes an entry

`set` on every YouTube download, zero `delete` or `clear` anywhere
(main.js:5170), and `yt-get-downloads` returns `[..._ytDownloads.values()]` — so
the map and the IPC payload grow for the life of the process.

### 3.6 [FIXED] `_scrollMemory` grows one entry per page ever visited

`const _scrollMemory = new Map()` (renderer.js:174) is written on every navigation
away and never pruned or capped, keyed by `page:navId`.

### 3.7 [FIXED] Ctrl+Z can silently undo something you did an hour ago

`pushUndo` (renderer.js:265) pushes `{label, fn, done}` for every undoable action.
An entry leaves the stack only if the user clicks Undo in the snackbar (which
expires after 5 s) or presses Ctrl+Z. Ignore both and it stays forever.
`undoLastAction` pops the most recent *un-done* entry whenever Ctrl+Z is pressed —
so Ctrl+Z in a long session reverts whatever destructive action was last left
un-undone, however long ago, with no confirmation and no indication of what it is
about to undo. Each retained closure also holds its snapshot, and library
operations snapshot liked tracks, play counts, play history, playlists and saved
queues.

**Fix.** Expire entries when their snackbar expires, or cap the stack at 1 and
make Ctrl+Z apply only to the action whose snackbar is still on screen. Either
way, show *what* is about to be undone.

### 3.8 [ALREADY FIXED] `dlState.done` grew unbounded

The persisted `abandoned` subset was capped at 5000; the in-memory map had no cap
or TTL. (A `pruneDlDone` was added in the last round — this entry records it so
the audit is complete, and flags that the cap interacts with 1.3: pruning a
`done` key silently makes that file requestable again, which is the right
behaviour but is currently an accident rather than a decision.)

### 3.9 [FIXED] The daily log is named by the UTC day while every other "day" is local

main.js:371 builds `papa-${new Date().toISOString().slice(0,10)}.log`; the stats
group by `new Date(ts).toDateString()` (local). Confirmed by execution under
TZ=Australia/Sydney: at 22:30 local the two disagree. This matters directly for
the forensic instructions in `docs/HANDOFF.md`, which tell the next session to
read `papa-<incident date>.log`: an evening incident is written to the adjacent
day's file.

**Fix.** Build the filename from local date parts.

### 3.10 [FIXED] The YouTube sign-in poll never gives up on its own

Independently of 0.2, the 1.5-second cookie poll in `yt-auth-start` has no
deadline — nothing stops it but the window closing, so an abandoned sign-in window
polls the session store every 1.5 s for as long as the app runs.

### 3.11 [FIXED] The browser extension cannot send the same command twice

`readCmd` (main.js:832) compares against `_lastCmd` and returns early on a match
**before** clearing the file. So the second "next" is ignored, the file is never
emptied, and every later poll re-reads the same value and ignores it again — the
command stays stuck until a *different* command arrives. Pressing next twice from
the extension advances one track.

**Fix.** Clear the file whenever a command is read, before the dedup check; dedup
on a timestamp or a nonce the extension writes, not on the payload.

### 3.12 [FIXED] Every drag and slider interaction is mouse-only

The app registers no `touchstart`/`touchmove`/`touchend` and no
`pointerdown`/`pointerup` anywhere — confirmed by inventorying all 40 event types
it listens for. The progress bar, volume slider, queue drag-to-reorder, sidebar
resizer, queue-panel resizer and Discover swipe are all built on
`mousedown`/`mousemove`/`mouseup`, so none works by touch or stylus, even though
plain clicks do.

**Fix.** Pointer Events replace all three mouse handlers with one API and cover
mouse, touch and pen. `makeDraggable` is the single choke point for two of the six.

## Tier 4 — interaction and input

### 4.1 [FIXED] The Discover cards are announced as buttons and Enter does nothing

`.discovery-swipe-card` is in the a11y sweep's selector list (renderer.js:6897),
so it gets `tabindex="0"` and `role="button"`, and the delegated Enter/Space
handler calls `card.click()` (11705). But the only handlers are `mousedown` and
`mouseup` on the `#discovery-swipe` container (7060, 7064) — there is no `click`
listener anywhere for that class. Confirmed by checking all 20 focusable classes
for a real click handler with the a11y selector lists excluded from the search:
19 have one, this one does not.

**Fix.** Add a `click` handler on the container that navigates, and keep
mousedown/mouseup only for the swipe-distance test.

### 4.2 [FIXED] MPRIS Play, Pause and Stop do nothing

`initMpris` sends `'play'`, `'pause'` and `'pause'` on the `media-key` channel
(main.js:1718-1721), and the renderer's handler understands only `'play-pause'`,
`'next'` and `'prev'`. Confirmed by listing every command main sends against the
handler's branches: three of the six are unhandled. A desktop applet's dedicated
Play button, its Pause button and its Stop button are all inert; only the combined
toggle works — and a headset's play button usually maps to Play, not PlayPause.

**Fix.** Handle `'play'`, `'pause'` and `'stop'` in the renderer. `stop` should
stop, not pause.

### 4.3 [FIXED] Shuffle can pick the track that is already playing

`pickShuffleIndex` excludes `state.queueIndex` inside the retry loop but its final
fallback is a bare `Math.floor(Math.random() * queue.length)` with no exclusion.
Measured over 200,000 runs: on a 12-track single-artist album (this app's primary
case, where the artist filter makes every candidate "recent" until attempt 8) it
returns the current track 0.07% of the time; on a 2-track queue, **12.5%**.

**Fix.** Exclude `state.queueIndex` in the fallback too, and if the queue has more
than one track never return it.

### 4.4 [FIXED] The seek-preview tooltip has no CSS rule, so it is unpositioned

`.progress-tooltip` (index.html:395) appears in no rule in styles.css — confirmed
by matching every class applied in markup against every selector in the
stylesheet. In the main player bar the handler sets only `display:block` and
`left` (renderer.js:12032); with no `position` the `left` is ignored and the div
joins the normal flow **inside the thin `.progress-track`**, so hovering the bar
distorts it. In the now-playing modal the handler sets `position:fixed` inline but
there is still no background, padding, colour, radius, z-index or
`pointer-events`, so the time reads as bare text over whatever is beneath it.

### 4.5 [FIXED] The library-scanning screen shows no spinner

`showLoading` (renderer.js:1165) renders `<div class="loading-wrap"><div
class="spinner">`, and neither class has any CSS rule, so the spinner is a
zero-size empty div. This is the screen shown during the first full scan — the
longest wait in the app.

### 4.6 [FIXED] The voice-search button has no visual state while listening

The mic handler adds and removes `.listening` five times (renderer.js:11513-11543)
and no CSS rule for `.listening` exists. Confirmed by cross-checking every
`classList.add/toggle/remove` literal against styles.css.

### 4.7 [FIXED] Multiple timestamps on one LRC line leave a raw timestamp in the lyrics

Standard LRC repeats a chorus as `[00:10.00][00:20.00]same line`. `parseLrc`
(lyrics.js) takes the first timestamp and leaves the rest in the text. Confirmed
by execution: the parsed entry is `{time: 10, text: "[00:20.00]same line twice"}` —
the panel displays the literal `[00:20.00]` and the line never highlights at its
second occurrence.

**Fix.** Loop the timestamp prefix, emitting one entry per timestamp with the same
text.

### 4.8 [FIXED] Right-clicking cover art does something different from the card

`.album-card-art` has its own `contextmenu` handler (renderer.js:7134) that
`stopPropagation`s and copies the file path, so right-clicking the largest part of
an album card gets "Path copied" instead of the album context menu. Not a
malfunction, but it is the one context-menu surface in the app that behaves
differently from its parent, and it is the easiest part to hit.

### 4.9 [FIXED — the claim was partly wrong] The artwork progress bar lags its own label

`fillEl.style.width = Math.round((i / missing.length) * 100)` (renderer.js:1108)
is computed before each item rather than after, so it runs 0% … (n-1)/n.

**Correction made while fixing.** There *is* a `fillEl.style.width = '100%'`
after the loop, so the claim that it never reaches 100% was wrong. The real
defects were that the bar read (i)/n while the text beside it read (i+1)/n — so
on a one-album fetch the bar sat at 0% for the whole wait — and that a cancel
snapped the bar to 100% and then wrote "Cancelled" underneath it. Both fixed.

## Tier 5 — numbers, dates and formatting

### 5.1 [FIXED] The elapsed-time readout shows an em dash for the first second of every track

`fmtDur` returns `'—'` for any falsy input, and `_fmtTimeCur` calls `fmtDur(ct)`
with the current position — which is `0` at the start of every track. In
"remaining" mode the same guard renders `-—` as the track ends.

### 5.2 [FIXED] `fmtDur` has no hours component

`fmtDur(3600)` gives `"60:00"` rather than `1:00:00`, so hour-long files — live
sets, DJ mixes, classical single movements — read as minutes. `fmtDur(-1)` gives
`"-1:-1"`.

### 5.3 [FIXED] Download ETAs over 24 hours are wrong by a day or more

`_hmsToSecs` does `(hms||'').split(':')` and treats the first field as hours.
slskd returns .NET TimeSpans, which serialise as `d.hh:mm:ss` past a day.
Confirmed by execution: `"1.02:03:04"` (1d 2h 3m 4s = 93784 s) parses as 3856 s
and displays as "1h 4m"; `"2.00:00:00"` displays as "2h 0m". A single-field value
is read as hours, so `"30"` becomes 30 hours.

### 5.4 [FIXED] `_fmtBytes` has no TB unit and shows sub-kilobyte sizes as KB

A 1 TB figure renders as "1024.00 GB" — relevant because the storage report totals
a multi-terabyte library — and a 1-byte file renders as "0.0 KB" because the `B`
branch only fires for exactly zero.

### 5.5 [FIXED] `detectSurround` treats a space as the `5.1` separator

src/slsk-filters.js:15 — `/(^|[^\d])5[\s._-]1(ch)?([^\d]|$)/i`. Confirmed by
execution: `"Beethoven Symphony 5 1st Movement"`, `"Bach BWV 5 1 Aria"` and
`"Disc 5 1 of 3"` all return `{kind:'ch51', label:'5.1'}`. The comment above the
table says the separator was made mandatory precisely to stop `"Album 51 Greatest
Hits"` matching — `\s` reintroduces the same class of error.

This is not only a badge: `g._sur` is a **sort key** for search results
(renderer.js:8663), it drives the surround-only filter and the count (8728), and
at 10709-10716 a falsely-surround anchor **excludes genuinely matching folders**
from an album download group. It also runs on YouTube titles (3063).

**Fix.** Drop `\s` from the separator class, or require a word boundary and no
adjacent digit-or-ordinal (`5 1st` must not match).

### 5.6 [FIXED] `normalizeName` eats letters out of album titles

src/library-manage.js:26 does `out.split(EDITION_WORDS[i]).join(' ')` — a plain
substring replace with no word boundary — and the list has `'remaster'` before
`'remastered'`, so the longer word is destroyed by the shorter. Confirmed by
execution:

- `"The Snow Goose (Remastered)"` → `"the snow goose"`
- `"The Snow Goose Remastered"` → `"the snow goose ed"`
- `findDuplicates([both])` returns `[]` — the two spellings of one album are not
  seen as duplicates.

It also mangles legitimate titles: `"Editions of You"` → `"s of you"`,
`"Remastered Live"` → `"ed live"`, `"Stereo"` → `""`, `"Deluxe Edition"` → `""`.

**Fix.** Word-boundary regexes built once, longest-first, and never strip a word
that is the entire remaining title.

### 5.7 [FIXED] The two download-state classifiers disagree

`_dlCategory` (renderer.js) and `dlClassify` (main.js) split slskd's state strings
differently. Confirmed by running both over the states slskd emits:

- `'Scheduled'`: renderer says **failed**, main says active. The renderer's own
  `_dlStateLabel` maps `'Scheduled'` to the label "Waiting" — so a scheduled
  transfer appears in the **Failed** tab labelled "Waiting".
- `'Failed'` / `'Aborted'` without a `Completed,` prefix: main says **active**,
  because `dlClassify` only checks whether the string *starts with* "Completed".
  The scheduler treats a failed transfer as still running and never records the
  failure, so the file is not re-sourced until the 20-minute stall timer.
- An empty or unknown state: renderer says failed, main says active.

**Fix.** One classifier in a shared module, used by both, with a test enumerating
every state slskd emits.

### 5.8 [FIXED] A null `eq` in stored settings stops the engine from ever starting

`normalize(settings = {})` in eq.js defends against `undefined`, not `null`, so
`buildAfGraph(null)` throws inside `_args()`, inside `start()` — reported as a
confusing `start-error` with no audio at all. Reachable through
`getPlayerSettings()`, which spreads the persisted `playerSettings` over the
defaults, so a stored `eq: null` wins. Latent today (the preset path guards with
`if (!preset) return`), but one hand-edit or one bad write makes the app silent.

**Fix.** `normalize(settings)` should coerce: `settings = settings || {}`.

## What was checked and came back clean

Recorded so the next pass does not repeat it, and so the five discarded candidates
are not re-investigated:

- **No undefined function calls.** Every `name(` in the renderer scripts resolves.
- **No duplicate DOM ids** in index.html.
- **No `data-*` asymmetry** — the two that looked orphaned are read by CSS
  attribute selectors.
- **No unescaped interpolation into `innerHTML`.** `highlightMatch` escapes its
  query correctly; every candidate my sweep flagged turned out to be a `src`
  assignment, `textContent`, a cache key or a toast.
- **No `reduce` without an initial value**, no `Math.max(...arr)` on a possibly
  empty array, no `for...in` over an array, no `typeof x === '<impossible>'`, no
  `RegExp` built from unescaped user input.
- **The queue drag-to-reorder index maths is correct** across all 250
  (src, dest, insertBefore, queueIndex) combinations on a 5-track queue.
- **`library-prune`'s folder-move remapping is correct** — `renamePlan` emits
  per-file remaps, as its comment claims. I misused the API and had to retract.
- **`toggleShuffleWrap` / `cycleRepeatWrap` are used** as command-palette actions.
- **`jumpback-card` has a click handler**, bound by id rather than class.
- **`makeDraggable` is guarded** by `modal._draggableSetup` and cannot accumulate
  document listeners.
- **The queue-panel resizer removes its own mousemove/mouseup**; the sidebar
  resizer binds once inside `setupListeners`.
- **`loadArtistBio` guards its late render** against page and artist identity.
- **Every context-menu surface** either appears in `CTX_SURFACES` or calls
  `stopPropagation`.
- **`queue-repair`, `surround-verify`, `format-badges`, `library-sig`,
  `download-spread`, `slsk-presence`, `slsk-tree`, `multi-select` and `history`**
  all passed semantic probes.

## What this audit could not reach

Everything here came from executing modules and cross-checking sources. Three
classes of bug are structurally out of reach without the app running on the
Fedora machine, and they are where the remaining defects will be:

1. **Render order and layout.** Whether a panel overlaps at 1920x1080 and at
   3840x2160 @1.7 scaling, whether a modal traps focus, whether a long album title
   overflows its card. None of this is visible from source.
2. **Event double-binding after re-render.** I verified the binders that are
   guarded; proving the rest requires counting listeners on a live node after N
   navigations. `getEventListeners($0)` in devtools, or a CDP script that navigates
   all ten tabs 50 times and reports listener counts per node.
3. **Behaviour under real duration.** The growth in Tier 3 is arithmetic — the
   question is what it costs after four hours of an album-a-side session with
   downloads running. Heap snapshots at 0/1/4 hours would answer it.

**The single highest-value next step is a CDP harness that drives all ten tabs**,
because it converts all three of those into mechanical checks. `.qa/` already has
`cdpd.js` and `ev.js` on that machine; `tools/mpv-probe.js` and
`tools/fault-inject.sh` in this repo cover the engine side.
